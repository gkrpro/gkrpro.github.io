About Decision Records

Decision records document security choices with full rationale. Each record captures: what we decided, why we decided it, what risks we accept, what compensating controls we implement, and who agreed. This transparency builds trust and creates institutional memory.

Block AI-Related Cloud Deployments Pending Security Maturity

DR-2025-001
Blocked
Decision Date Q1 2025
Stakeholders Cloud Domain Lead, Cloud Architect, Security Leadership
Review Date Q2 2025

Decision Statement

All AI-related cloud resource deployments are blocked until security maturity thresholds are met across four dimensions: defined threat models, mature control implementations, team capability, and established measurement criteria.

Context & Rationale

AI/ML capabilities in cloud environments are evolving rapidly. Threat landscape, control maturity, and organizational capability are all nascent. Deploying without foundational clarity creates unquantifiable risk.

Technology immaturity threshold model assessment:

  • Threat models: Undefined (no agreed attack trees, attacker profiles, or vulnerability classes for AI-specific threats)
  • Control implementations: Immature (control frameworks exist but are not battle-tested in production)
  • Team capability: Absent (no security team members with AI/ML threat modeling expertise)
  • Measurement criteria: Not established (no agreed success/failure metrics for AI security controls)

What Changes This Decision

Deployment can proceed when ALL four criteria are met:

  • Threat models published and reviewed by external security experts
  • Controls documented with evidence of real-world validation
  • Team includes at least two individuals with AI security certification/experience
  • Measurement criteria agreed with CISO, risk, and business sponsors

Compensating Controls

While AI deployments are blocked, we are actively:

Threat Modeling: Using the AI Risk Repository v3 to map threat landscape. Publishing monthly risk updates.
Control Development: Building control frameworks specific to AI workloads on Azure. Documenting implementation patterns.
Team Capability: Funding AI security certifications. Building partnerships with external AI security experts. Scheduling quarterly threat modeling sessions.
Measurement: Defining success metrics for AI security controls. Establishing baseline capability assessments.

Risk Acceptance

We accept the risk of slower AI/ML capability deployment. Business teams may perceive this as a blocker. The alternative risk (deploying immature AI without foundational security clarity) is considered unacceptable.

Stakeholder Alignment

CISO: This is a defensible risk position grounded in technology maturity, not arbitrary obstruction. Business Leads: We're unblocking AI deployment by accelerating maturity work, not indefinitely saying no. Architects: This clarifies the path: build security foundations first, then deploy.

Approve Multi-Cloud Control Framework Implementation (SCF + Azure-First)

DR-2025-002
Approved
Decision Date Q1 2025
Stakeholders Cloud Domain Lead, Architects, Security Leadership
Implementation Status In Progress

Decision Statement

Adopt the Security Cloud Framework (SCF) as the control baseline. Implement across Azure first. Design service equivalence mappings for AWS and GCP to enable future multi-cloud expansion without rearchitecting.

Rationale

Why SCF: Comprehensive, cloud-agnostic, and aligned with organizational risk appetite. Better baseline than building custom frameworks from scratch.

Why Azure-first: Organization's primary cloud platform. Faster to implement and validate. Service equivalence mappings create clear path to multi-cloud without thrashing on control differences.

Implementation Approach

  • Map SCF controls to Azure services (complete)
  • Document implementation guidance for each control
  • Create service equivalence matrices for AWS/GCP
  • Pilot with three archetype implementations
  • Iterate based on operational feedback

Trade-offs Accepted

Customization: SCF is more comprehensive than we need today. We accept some over-scoping rather than building incrementally and refactoring later.

Timeline: Full multi-cloud equivalence takes time. We prioritize Azure momentum while preparing for AWS/GCP later.

Success Criteria

  • All SCF controls mapped to Azure services by end Q2
  • Implementation guidance completed and peer-reviewed
  • AWS/GCP equivalence matrices drafted by end Q3
  • First archetype implementation operational by end Q2

Accept Risk: Delayed Data Residency Controls in Online-Disconnected Archetype

DR-2025-003
Risk Accepted
Decision Date Q1 2025
Stakeholders CISO, Legal, Data Governance, Cloud Architecture
Review Date Q3 2025

Decision Statement

Accept risk of delayed data residency control implementation in the Online-Disconnected archetype for 90 days. Compensate with procedural controls and enhanced monitoring.

Risk

Data may be processed or replicated outside approved geographic boundaries. Potential compliance impact for regulated data (PII, payment data). Estimated probability: medium. Estimated impact: moderate (notification required, but no expected enforcement action if controls are deployed within 90 days).

Why Not Wait?

Azure service availability in approved regions has maturity gaps. Waiting 6+ months for native residency controls blocks business initiatives. Compensating controls mitigate risk to acceptable level.

Compensating Controls

Procedural: All data flows reviewed for geographic processing before workload deployment.
Monitoring: Automated alerts for data processing outside approved regions. Daily review logs.
Access Control: RBAC restrictions prevent unauthorized data movement.
Audit: Monthly residency control audit. Escalation triggers if violations detected.

Path Forward

  • Target: Deploy native Azure data residency controls by end Q2
  • Interim: Compensating procedural and monitoring controls in place by end of week
  • Audit: Weekly residency compliance review during grace period
  • Escalation: Any violations immediately escalated to CISO
